# Verify Stella

Run every command from the root of a Stella repo checkout (local folder `stella-v2`); paths below are relative to it. When this skill was loaded from `~/.stella/skills/verify-stella`, that folder links into the checkout it came from: `cd "$(dirname "$(realpath ~/.stella/skills/verify-stella/SKILL.md)")/../../.."`. To verify a branch, run the same paths from a worktree of that clone or a separate clone.

Establish whether the requested behavior works in the real product. Use your judgment to choose interactions, coverage, and evidence based on the change and what you observe. The feature map is product context and a collection of examples, not a required test suite.

## What to prove

Start from the user's claim or the regression being fixed. Choose a realistic situation that would distinguish correct behavior from the suspected failure. The diff, nearby source, and live app can help identify affected states; consult the relevant [feature notes](features/README.md) when they add useful context. Adapt dated recipes to the current product.

Coverage should follow the mechanism and risk. A search change may need a result-to-destination interaction; a saved preference may need reopening or relaunching; a startup race may need a fresh launch. Exercise additional entry points when they have distinct behavior or could expose the same failure. A small visual edit does not imply a tour of every feature.

Match evidence to the claim. Show the real user action and its result. Read back mutations where persistence or downstream effects matter. Use screenshots for appearance, semantic state for control behavior, and traces or profiles for responsiveness. A still screenshot cannot establish smooth animation. Capture any "before" while you first reproduce the problem, before changing code; never rebuild, stage or check out old code afterwards just to get one, since an "after" alone is usually enough. Store evidence in the run's `evidenceDir` (`session info`; `~/.stella/outputs/verify-stella/<runId>/` on Stella machines), never only inside a worktree: removing the worktree deletes it, and the user cannot open it from another device.

Unit tests are not evidence, and are banned in this repo (AGENTS.md): prove a change in the real product, plus typecheck, lint and build.

A helper succeeding proves only what it actually observed. A healthy shell is not a working feature; a submitted message is not a completed agent task; a visible provider error demonstrates an error path, not a successful response. Report what passed, what failed, and what remains unverified, with enough evidence to support those distinctions. Missing prerequisites should identify the affected claim and the concrete blocker.

## Where test copies run

- **Which machine.** The user's standing rules say where test copies run and how many the Mac takes. macOS-only behavior (computer use, dictation fallback, Record screen, privacy prompts) needs the Mac; close each test copy there with `cleanup apply` as soon as its check is done.
- **Never from the installed app's checkout.** Never launch a test copy from the installed Stella's folder (`$STELLA_APP_DIR`, `~/.local/share/stella/app` on omarchy, the Mac install) or a git worktree of it: worktrees share refs, and a test copy's sync rewrote the install's update refs with dev-backend history and broke its Update. Work from the `stella-v2` clone, a worktree of that clone, or a separate `git clone`. `session launch` refuses with `INSTALLED_APP_CHECKOUT` when the checkout shares its git data with an installed app.
- **Personal drafts.** The user's installs can carry personal drafts that are not on master (for example a shared-logins or Board draft). They are not product features: don't document them here, and don't expect them in a test copy built from master.

## Available capabilities

The desktop CLI owns an isolated Electron instance and exposes inspection, interaction, diagnostics, and optional journey shortcuts:

```bash
node .agents/skills/verify-stella/control-stella.mjs help
node .agents/skills/verify-stella/control-stella.mjs capabilities
node .agents/skills/verify-stella/control-stella.mjs session launch --account pro
```

A fresh worktree needs `bun run deps desktop` first and the gitignored `workers/cloud-builder/.dev.vars` copied in from the main checkout (mode 600; delete the copy with the worktree) so launch can mint a test account.

On Linux every run gets its own hidden X display (Xvfb on `:90` and up, unpacked into `~/.cache/stella-verify` without root by `scripts/fetch-xvfb.sh` when the system has none), so nothing opens on the user's screen; `--display host` uses the real display. macOS opens a real window. Test copies are muted: Electron and the test Chromium start with `--mute-audio`, so message sounds, read-aloud and voice never play on the user's speakers; pass `--audible` only for a claim about sound. The desktop is one conversation with no history or New chat control; launch a fresh run (`--replace`) when the claim needs an empty conversation. `session relaunch` restarts Electron, the runtime worker and the test browser, so runtime and engine edits load; it keeps the data, profile and account. Stop a run with `cleanup apply` (alias `stop`); the `session` group has no stop command.

Choose the account and initial state needed for the claim. Launch signs in a fresh dev test account by default; `--account pro`, other plans and `--account signed-out` (no account) are documented in the [desktop reference](references/desktop.md). Launch seeds onboarding complete unless you pass `--first-run`, which a first-run onboarding claim needs.

`inspect observe --path <directory>` captures semantic state, controls, Chromium accessibility, and a screenshot together; `--since <observation.json>` reports changes from a capture in the same run. Capture is sequential, not atomic. `inspect state`, `inspect components`, `inspect aria`, and `inspect screenshot` also expose individual views. `drive` provides clicks, fills, keys, scrolling, and waits. `chat`, `nav`, `settings`, and `apps` offer convenience macros (`nav open --name <place>` opens any place from the top bar's + menu). Choose whichever gives an understandable interaction with the current UI; there is no requirement to use a named journey first. If a macro's assumptions no longer fit, inspect the app and use the underlying controls, and fix the macro. `<group> <command> --help` (or `capabilities`) lists a command's options and ranges; unknown options are rejected. Every command prints one JSON envelope (`ok`, `command`, `data` or `error`, `meta`); `ok` means the command ran, not that the product passed. `settings` macros report shell state, not dialog contents.

For how long Update takes (a draft applied until Stella is back and usable), `scripts/update-bench.mjs` runs a sandbox clone through this harness and times each kind of change (renderer, main, runtime, dependencies, a stale draft, undo) with a per-step breakdown; `node .agents/skills/verify-stella/scripts/update-bench.mjs help` lists its commands. Compare a change against its base with `sync --ref`, the same `--label` per side, and several iterations; the machine's noise is a few hundred milliseconds.

`session doctor` distinguishes shell, device identity, and runtime readiness. `diagnostics` and `performance` help explain failures and timing. DOM quietness from `drive settle` does not establish completion of network or agent work; it ignores animated decorative SVGs such as the top-bar mark, and `--ignore <CSS>` skips other known-decorative regions. `apps state` returns surface text without a readiness verdict. `chat send` distinguishes a new visible user message, a new notice, and a timeout; none establishes completion of an assistant response. Ambiguous click/fill targets return candidates; narrow them with `--within <CSS scope>` or a specific selector.

For cloud-side behavior, [cloud verification](references/cloud.md) describes `cloud-turn.mjs`, `backend-call.mjs`, Previews and executor diagnostics, including how to place a task on a test copy from a cloud chat. Headless execution can prove a cloud claim; it cannot establish the desktop dispatch or browser handoff that it bypasses.

For iOS, read the [iOS reference](features/ios.md). iOS work happens on the Mac: an agent elsewhere moves itself there. `scripts/control-stella-ios.sh` stages disposable source, boots a simulator, builds the dev app against the dev backend (`build`), signs it into a dev test account (`sign-in --plan pro`), and captures framebuffer proof; semantic input comes from XcodeBuildMCP. You may drive the simulator yourself or give the capture to a Mac subagent (GPT `codex/gpt-6.1-sol` is an option for simulator work; never give it code); the agent that owns the code keeps the code. Shut down your simulator and Metro when done.

## Accounts and sign-in

- **Dev test accounts** are the default everywhere: `session launch` mints `agent-<runId>@test.stella.local` on the dev backend (or `STELLA_BACKEND_URL`), `STELLA_VERIFY_ACCOUNT_EMAIL` reuses one, and `cloud-turn.mjs`, `backend-call.mjs` and the iOS `sign-in` mint the same way. They need the admin secret from `.dev.vars` and work only on dev and Previews.
- **Prod has no test accounts.** A prod check signs in the prod test account (named in the stella-verify area memory; keep it out of this public repo) by email link, opened in Stella's own browser; never click "Open Stella" on the callback page, paste the code into the test copy instead. After about four sign-ins from a test window in a few hours prod asks for a human check (Turnstile), which an agent cannot pass; fall back to a dev test account on the released source. Prod admin and test fixtures sit behind Cloudflare Access on purpose; don't work around it.
- **Never** use the user's own accounts, sessions or credential files in a test copy.

## Testing prompt changes

The desktop takes its prompts from the backend first (`packages/agent/src/host/desktop-sources.ts`: served bundle, revalidated every 5 minutes, edge-cached up to 5 minutes after a deploy) and falls back to the bundled files, so editing a prompt file changes nothing in a test copy on its own. Either deploy the prompt to your own Preview (`bun run preview -- up`) and point the run at it, or, in a throwaway worktree, swap that source to read the bundled file first (never commit the swap). Desktop prompt presets in Settings only feed the preview there. Prompt and model experiments run on Opus unless the user says otherwise; test brief behavior on the model in question (Haiku, the `--claude-login` default, copies chat-stated rules into briefs where Opus doesn't).

## Shared resources

Other agents and the user use the same machines. Each of these has bitten agents; take the isolated path by default.

- **Your run.** One run per checkout. `ALREADY_RUNNING` usually means another agent's run: leave it, and set `STELLA_VERIFY_RUN=<name>` on every command to keep your own. Run pointers (`.run/current*.json`) are replaced by rename, so a parallel launch's orphan sweep never reads a half-written one, and an unreadable pointer counts as still owned.
- **Processes.** Only stop processes you started, by the exact PID you recorded; never `pkill`/`killall` by name or pattern (a pattern in a command line matches your own shell). The harness signals a stored PID only while it is still the recorded process and logs every signal sent or refused to `logs/process-kills.log` under the data directory (the run's `data/logs/`; `~/.stella/logs/` for the installed app). A kill with no line there came from outside that code.
- **The browser extension.** The user's Chrome extension pairs with exactly one Stella (fixed port 39040, one native-messaging host per user). For a claim that needs the extension, `session launch --browser-extension` starts a private, muted Chromium on the run's display with its own copy of the extension paired to your run's bridge. It needs Chromium (`/usr/bin/chromium`, Playwright's, or `STELLA_VERIFY_CHROMIUM`); Google Chrome refuses unpacked extensions. `--browser-bridge shared` takes the real extension away from the user's Stella and every other run until the user relaunches: only for a claim about the user's own Chrome, and only after asking.
- **The backend.** Backend changes go to your own Preview, not dev. From `workers/cloud-builder`, `env -u CLOUDFLARE_API_TOKEN bun run preview -- up --name <name>` deploys your tree as an isolated backend (own Durable Objects and D1) and prints the URL to export as `STELLA_BACKEND_URL` for `cloud-turn.mjs`, `session launch`, `backend-call.mjs` or `curl`; `preview -- down --name <name>` when finished. A Preview cannot start agent containers (cloud Claude Code agents, cloud shell, app builds) or run account-key (BYOK) cloud turns; desktop and cloud turns on Stella models work there. Claims that need those go to dev: dev deploys need no asking, from a tree that contains origin/master (`deploy:dev` refuses anything else); say so in your report. Prod deploys wait for the user's go. See DEPLOY.md, "Previews".
- **Claude Code.** Runs start signed out. `--claude-login host` copies this computer's Claude access token into the run's own config, never the refresh token, so the user's login cannot be rotated or signed out; it lasts until the token expires (hours) and cleanup deletes it. It spends the user's Claude quota, so use it only when the claim needs a real Claude Code turn. Such a run starts on the Claude Code engine with Haiku already selected; keep it there unless the claim is about a specific model. `--claude-login token` uses `STELLA_VERIFY_CLAUDE_OAUTH_TOKEN` instead (for example your own `$CLAUDE_CONFIG_DIR/.credentials.json` access token, never printed) when the host login is at its limit or ended. Never copy credential files by hand. Cloud Claude Code needs no sign-in on dev: every test account's cloud runs it on a shared test login (`claude@test.stella.local`); [cloud verification](references/cloud.md) has the path.
- **The iOS simulator.** One Mac, at most four agent simulators at once, each slimmed with simslim by `boot` (no Siri, iCloud, StoreKit, push, widgets and more; `--stock` or `--except` when a claim needs them). Read [Slim simulators](features/ios.md#slim-simulators) before calling a simulator failure a Stella bug; see [iOS](features/ios.md).

## Isolation and evidence boundaries

Drive only the helper-owned Electron run recorded in `.run/current.json` (`.run/current-<name>.json` with `STELLA_VERIFY_RUN`), with its own home folder (`~/.stella` there is the run's data; on Linux the real `~/.stella` path is mounted over by it too), data and Chromium profiles. Never point a test app or its agents at a real-home absolute path such as `/home/<user>/.stella`: what lands there is the user's real Stella data and syncs to their real account. On Linux the jail covers only `~/.stella`, so a test task can still read other real paths and use the host's `gh` login. The run also isolates protected storage, saved secure values and the Claude Code and Codex CLI configs, but shares the OS user, the CLIs on `PATH`, the display (on macOS), and the network; the desktop reference lists exactly what is shared. The developer's window, the real `~/.stella`, and the Mac checkout are not verification fixtures. Keep cleanup limited to recorded owned resources; `cleanup plan` and `cleanup apply --dry-run` expose the targets. Preserve evidence and durable run data. Stop your run with `cleanup apply` before you finish, and before deleting the checkout (in a script, from a `trap … EXIT` or `finally`). The run records Electron's whole process tree, including helpers that detach (crash reporter, zygotes), and stops them before deleting its temp folder; a run whose checkout was deleted or that was never stopped is reaped by the next `session launch` or `cleanup apply` from any checkout. Likewise stop any mock server, browser, recorder or Xvfb you start yourself outside the harness, with a `trap` or `finally`, so none outlives your test.

Use observed controls and current geometry for input. Read-only eval can fill an observability gap, but internal setters or direct database mutations cannot substitute for the user path being tested. Fixture setup should be distinguishable from the action under verification. Do not expose credentials in diagnostics or shared artifacts.

## Maintaining this skill

Keep feature notes focused on product behavior, entry points, non-obvious dependencies, and useful source pointers. Examples can illustrate a tricky interaction without prescribing a complete run. Use whatever document structure communicates that information clearly.

Improve the harness when a recurring mechanical problem needs deterministic handling. Prefer richer observations and general interaction capabilities; add a journey macro when it saves repetitive navigation without hiding evidence needed to judge the result.

`node .agents/skills/verify-stella/scripts/check-feature-map.mjs` checks feature links, that every desktop command cited in SKILL.md, the references and the feature notes exists in the registry, and that every relative link resolves. It does not judge verification coverage or enforce a prose template.

This folder is the only copy. Stella agents see it through `~/.stella/skills/verify-stella`, a real folder whose entries are symlinks into the checkout (Stella's skill catalog skips a symlinked skill folder, and a real folder keeps `.run/` and `artifacts/` out of `~/.stella`). After adding a top-level file or folder here, rerun `.agents/skills/verify-stella/scripts/install-stella-skill.sh` on each machine.
